Implementación:
scripts/api-start-audit.sh comienza antes de los controles y del preflight.
Conserva en orden los dos controles de SHA iniciales, export explícito
API_INSPECTION_BOOT=1 NODE_ENV=development, ejecución del preflight existente,
control de SHA del bundle posterior y exec node --enable-source-maps del bundle.
No captura/redirige la salida de preflight ni los diagnósticos de sha256sum.
Conserva sus códigos de salida. No modifica runtime-preflight.mjs.
No modifica variables de modo adicionales. El logger hereda las variables
efectivas y registra exclusivamente NODE_ENV y API_INSPECTION_BOOT; antes del
export (fallo de guardas iniciales), registra los valores heredados, incluso null
si están ausentes. No vuelca el entorno, argumentos, secretos o salida preflight.

Cada salida controlada previa al exec intenta una sola línea JSON con UTC,
PID del shell, SHA-256 completo del bundle (o null y código de error de lectura),
modo efectivo, etapa, resultado preflight y código de salida. No se inventa un
hash si el archivo no existe. preflight=not_run no significa éxito; failed lleva
el código real; passed solo aparece tras salida cero del preflight.
Ante fallo previo al exec se usa startup_shell_no_api y api_exec_attempted=false.
En la ruta aprobada se escribe antes de exec, con el PID que hereda realmente
Node; exec_target y api_exec_attempted=true identifican INTENTO de exec, no una
afirmación de salud, escucha o éxito de inicio de la API. Si exec falla después,
la línea sigue siendo un intento, no una confirmación de proceso API iniciado.
No se puede conocer anticipadamente ese resultado con una línea anterior al exec.

El logger abre únicamente con O_APPEND, hace un solo write de la línea completa,
no reintenta escrituras parciales y nunca trunca, borra ni rota el archivo.
Si falla la escritura, emite advertencia sin detalles sensibles y el arranque
o rechazo continúa con el mismo código. En este filesystem local la concurrencia
de doce procesos preservó doce líneas JSON independientes. No se promete
atomicidad en filesystems remotos ni ante un write parcial/disco lleno; una
escritura fallida puede no dejar una línea completa. SIGKILL, caída de máquina
o preflight que no termina tampoco permiten garantizar una línea final.
Estas limitaciones no se ocultan como registros exitosos.
