Análisis estático de las 28 fuentes marcadas como creadoras (o creadoras condicionales) de usuarios en reports/inventario-suites-poblacion.html. La pregunta se responde a nivel de suite: ¿se pueden eliminar todas sus filas de usuarios y operar con el ADMIN canónico, o queda al menos una identidad propia funcionalmente necesaria?

Respuesta corta. Bajo la unidad de conteo funcional revisada, 3 suites pueden ser seed-only y 25 suites todavía contienen una necesidad de identidad/estado adicional. “Puede reutilizar el ADMIN” no significa que la suite pueda ser aprobada: las 28 siguen teniendo fixtures de negocio, permisos, sesiones o estados fuera del seed según el inventario anterior.

Base de comparación y regla de conteo

  • Seed ADMIN garantizado: lib/db/src/seed.mjs:272-277 inserta o conserva usuario='admin', rol='ADMIN' y ubicacion_id=NULL; la contraseña llega por ADMIN_SEED_PASSWORD (:15-24). El seed crea ubicaciones en :175-196, pero no crea usuarios CAJA, BODEGA, TERMINAL, SUPERVISOR, SISTEMAS o CONTADOR.
  • Seed-only (3): todas las filas de usuario de la suite son sustituibles por el ADMIN canónico sin cambiar una identidad, rol, autorización, alcance o estado que el caso afirme. Esto incluye usuarios usados solo como FK/actor nominal, no como permiso probado.
  • Mixta (17): el ADMIN de la fuente es conceptualmente sustituible por el seed, pero la suite también autentica y afirma un rol/alcance no ADMIN, o necesita una combinación de identidad, sitio, permiso o estado que el seed no garantiza.
  • Identidad propia (7): cuatro suites necesitan además un ADMIN distinto por identidad/estado/competencia, y tres no crean ADMIN alguno y prueban roles no ADMIN. En ambos subgrupos la sustitución completa por el seed es imposible.
  • Una fila de usuario insertada para provocar una carrera de unicidad, una confirmación separada, un filtro por actor o un estado inactivo afirmado cuenta como identidad propia aunque también tenga rol ADMIN (o aunque el rol escrito sea solo una convención). No se confunde “rol igual” con “misma identidad”.
  • Prueba mínima de rol: crear CAJA/BODEGA no basta. Aquí se cuenta como necesidad funcional solo cuando la fuente autentica esa sesión y afirma un 403, una respuesta/alcance distinto, una redacción por rol, una autorización, o una relación de auditoría/estado que exige una identidad distinta. Un usuario que solo aparece como usuario_id/FK se trata como nominal y puede mapearse al seed ADMIN.
Credenciales y otros usuarios. “Sustituible” es una conclusión funcional, no un parche mecánico a estas fuentes. Las suites que hoy calculan una contraseña propia necesitarían que el harness conozca la credencial del seed o cree una sesión para el ID canónico. La comparación no presupone usuarios preexistentes fuera del seed canónico: un SELECT del primer usuario activo, o un literal como usuarioId=1, no reduce el conteo ni demuestra qué identidad garantiza el seed.

El motivo es segundo actor/objetivo de unicidad, confirmador o filtro por identidad/sitio; el mismo rol no implica la misma fila. security-api queda en mixtas: su ADMIN adicional aísla fixtures, pero no es una identidad separada exigida por una aserción.
  • 3 sin ADMIN: equipos, proveedores-alcance-fechas y role-access-matrix. Sus escenarios necesitan BODEGA/SUPERVISOR u otros roles no ADMIN.

Criterio aplicado. El conteo ya usa el seed canónico, no un estado arbitrario de la base: el ADMIN que el seed garantiza permite cubrir el actor/FK nominal de las tres suites seed-only. No se infiere necesidad por el texto CAJA/BODEGA de un INSERT; se exige una aserción concreta de autorización, alcance, redacción, estado o identidad. Tampoco se presenta ninguna de las 25 suites como autorizada a poblar fuera del seed: “necesidad funcional” describe lo que el caso actual afirma, y la regla seed-only sigue bloqueándolo.
