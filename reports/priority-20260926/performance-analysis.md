### Credit semantics that must survive any proposed optimization

`reportes-commercial.ts:71-96` filters accounted tickets by effective accounting dates, authorized locations, terminal user, selected clients, invoiced flag, product/fabric/color/unit/supplier existence, modality and payment-method existence. Matching product filters select WHOLE tickets; only modality additionally filters summed lines. Do not convert EXISTS into a join that duplicates amounts.

* Summary sales = SUM(selected-line importe); ticket count counts matching tickets. Exact utility is NULL if any selected line lacks frozen cost; otherwise SUM(importe - costo_total_congelado) (`174-188`). Group rows use the same rule; ticket average is sales/ticket count (zero when no tickets).
* Payment amount per method/modal component = SUM(tp.importe × component_subtotal / NULLIF(ticket_subtotal,0)); operations count DISTINCT payment IDs **per component** (`190-199`). Do not sum component operation counts as unique total operations; do not replace proportional subtotal allocation with whole payment or rounded-per-line amounts.
* Frequency risk = current tickets / previous tickets < 0.5; previous<=0 gives SIN_HISTORIAL (`34-36,217-219`). Current latest purchase uses MAX(t.created_at), not effective accounting time (`181`).
* FIFO receivable rows include every returned charge, including zero pending charges (`225-230`). Amount is pendienteCents/100; total is sum of ALL these rows, not current visible page. Aging uses today's UTC date string and due date; no due date => Sin plazo, days<=0 => Vigente, then 1–30/31–60/61–90/91+. It is NOT aging at report end.
* Credit projection is GLOBAL complete historical ledger of active non-system clients, restricted only by explicit client IDs (`207-224,236`). Period/site/product/modality must NOT prefilter its ledger: that resets FIFO opening debt/favor. Debt and favor must stay separate; balances cannot be replaced by signed SUM(movimientos.importe). Preserve directed applications, reversal links, immutable-applied cents, historical preventImplicitFavor and full ordering (`credit-aging-read-model.ts:116-150,240-281`).
* Directed payments embedded in clientes currently use approved status and created_at date range, with no site predicate (`201-206`); the separate resolved-requests report includes approved AND rejected, COALESCE(resuelta_at,created_at) and site filter (`reportes.ts:209-237`). They are not interchangeable queries.
* Existing generic totals helper converts NULL/nonfinite numeric input to zero (`commercial:15-30`), including utility totals, although per-client unknown utility remains NULL. An “optimization” must not silently change this behavior; any correction is a separate financial decision.

### Credit options — NOT implemented; require approval

1. **Presentation pagination/windowing of tables, retain complete API result and full server totals.** Reduces React/DOM work, not ledger SQL or transfer. Sort full data before slicing; keep totals/export all rows and accessible page controls. Browser find/print semantics require an explicit full-export/print path. Removing zero-balance rows or taking top-N changes information and is not implicit approval.
2. **Chart top-N plus explicit Other aggregate.** Cuts Recharts work; changes chart presentation, not sales sums, if Other sums omitted clients exactly. Must disclose grouping and retain full table/export. This is a user-facing choice, not a silent performance patch.
3. **Parallelize independent report query waves with bounded concurrency.** Keep exact SQL and canonical projection; may shorten critical path but increase pool contention under load. No new cache or index. Assess snapshot consistency: current queries already lack a shared transaction; stronger consistent-snapshot behavior is a separate change.
4. **Optimize ledger evidence retrieval or canonical projector only after CPU/SQL profiling.** Keep every full ledger and cents-level result identical (debt/favor, each charge, allocation/reversal/directed evidence). Needs differential fixtures including reversals, prepayments, historical markers, zero charges and mixed modality; cannot use signed sums or period-filtered balances.
5. **Separate cold navigation benchmark from in-app navigation benchmark.** Clarifies bootstrap costs; does not itself improve product performance. Preserve original cold metric rather than relabeling the faster metric as the same acceptance test.

Preserve total=all matched customers, page metadata, activity site restrictions, global debt/favor, nonfinancial nulls, permissions and transaction.
