# PARTE 1 — Direcciones separadas

El cliente hoy tiene un solo campo `direccion`. Se separa en dos:

- **Dirección particular** — el campo actual `direccion` se renombra a `direccion_particular`. Conserva los datos existentes.
- **Dirección de entrega** — campo nuevo `direccion_entrega`, opcional.

**En el formulario:**
- Los dos campos, cada uno con su etiqueta clara
- Casilla **"La misma que la particular"** que copia el contenido de un campo al otro. Ahorra capturar dos veces el caso común.

**Dónde se usa la dirección de entrega:** en las hojas y documentos donde haya que mandar mercancía. Si está vacía, se usa la particular.

# PARTE 2 — INE del cliente

Campo nuevo para subir la identificación oficial.

## Almacenamiento

- Nueva tabla `cliente_documentos`: id, cliente_id (FK), tipo (por ahora solo `INE`), nombre_archivo, ruta_archivo, mime_type, tamano_bytes, subido_por (FK usuarios), subido_at
- Acepta imágenes (JPG, PNG) y PDF
- Tamaño máximo 5 MB por archivo
- Se pueden subir **hasta dos archivos** por cliente, para frente y reverso
- Reemplazar un archivo conserva el anterior en historial, no lo borra

## Acceso restringido

**Solo ADMIN puede ver, subir, reemplazar o descargar el INE.**

- Ningún otro rol ve la sección de INE en el perfil del cliente, ni siquiera vacía o deshabilitada
- El endpoint que sirve el archivo valida el rol **en el servidor**. Un usuario que no sea ADMIN recibe **403**, aunque conozca la URL directa.
- La ruta del archivo **no debe ser adivinable**: usa identificadores aleatorios, no el id del cliente
- Los archivos **no se sirven desde una carpeta pública**. Se entregan a través de un endpoint que valida la sesión y el rol en cada petición.

## Registro de consultas

Cada vez que alguien ve o descarga un INE, se registra en `auditoria`: quién, cuándo, de qué cliente y qué acción (ver o descargar).

Motivo: es un documento de identidad oficial y hay que poder rastrear quién lo consultó.

## En la interfaz

- Sección **"INE"** dentro de la pestaña de Datos del cliente, visible solo para ADMIN
- Muestra vista previa de las imágenes, o el ícono de PDF con el nombre del archivo
- Botones para subir, reemplazar y descargar
- Indica quién lo subió y cuándo
- Al subir, aviso discreto de que el documento queda con acceso restringido y su consulta se registra

# PARTE 3 — Orden alfabético

**Todos los listados de clientes se ordenan alfabéticamente por nombre de forma predeterminada.**

- Orden alfabético con reglas de español: los acentos no alteran la posición, y la Ñ va después de la N
- **"Venta a Público" siempre aparece primero**, antes del orden alfabético, marcado visualmente como cliente del sistema
- El usuario puede reordenar por otras columnas si quiere, pero al entrar siempre arranca en alfabético
- Aplica en: el listado principal, el selector del POS, el selector de cobro a crédito, los reportes y cualquier otro lugar donde se listen clientes

**Aplica el mismo criterio a proveedores**: orden alfabético por nombre de forma predeterminada.

# PARTE 4 — Borrado de clientes

## Reglas

**Un cliente se borra de verdad solo si nunca tuvo movimientos.** Si ya operó, se desactiva, porque borrarlo dejaría tickets y movimientos apuntando a un cliente inexistente y descuadraría los reportes.

| Situación | Qué pasa |
|---|---|
| Sin tickets, sin movimientos de crédito, sin saldo | **Se borra** de la base |
| Con historial pero **sin saldo pendiente** | **Se desactiva.** Conserva su historial y deja de aparecer en selectores |
| Con **saldo pendiente no vencido** | **Se rechaza.** Mensaje: "Este cliente tiene un saldo pendiente de $X. Liquida el saldo antes de darlo de baja." |
| Con **saldo vencido** | Requiere **autorización de ADMIN con contraseña**, y el saldo se registra como pérdida. Ver abajo. |

**El cliente "Venta a Público" no se puede borrar ni desactivar** bajo ninguna circunstancia.

## Baja con saldo vencido

Cuando un cliente tiene saldo vencido y se le quiere dar de baja, ese dinero se da por perdido. Es una decisión con consecuencia contable, así que:

1. Modal que pide **usuario y contraseña de un ADMIN**, aunque quien lo esté haciendo ya sea admin. Es una confirmación deliberada, no un permiso.
2. **Motivo obligatorio**, mínimo 20 caracteres
3. La pantalla muestra con claridad el monto que se va a dar por perdido y desde cuándo está vencido
4. Al confirmar, en una sola transacción:
   - Se genera un movimiento de crédito tipo `AJUSTE` con importe negativo igual al saldo, dejando la cuenta en cero
   - Ese movimiento se marca como **incobrable**, con su motivo
   - El cliente se desactiva
   - Se registra en auditoría: quién autorizó, quién lo ejecutó, el monto y el motivo
5. **No se borra nada.** El historial completo se conserva.

## Reporte de cuentas incobrables

Nueva vista para ADMIN dentro de Clientes: lista de todos los saldos dados por perdidos, con cliente, monto, fecha, quién lo autorizó y el motivo. Con totales por periodo.

Es información que necesitas para tu contabilidad y para saber cuánto te ha costado el crédito.

## Reactivar

Un cliente desactivado se puede reactivar desde su perfil, con registro en auditoría. Si tenía saldo dado por incobrable, ese movimiento **no se revierte**: el historial queda como está.

# LO QUE NO DEBES HACER

- No permitas que ningún rol distinto de ADMIN vea, suba o descargue un INE
- No sirvas los archivos de INE desde una carpeta pública
- No uses el id del cliente en la ruta del archivo
- No borres un cliente que tenga historial de movimientos
- No permitas dar de baja a un cliente con saldo pendiente no vencido
- No permitas dar de baja con saldo vencido sin contraseña de ADMIN y motivo
- No borres ni revierta el historial al dar un saldo por incobrable
- No permitas borrar ni desactivar a "Venta a Público"
- No pierdas los datos del campo `direccion` al renombrarlo
